# AGENTS.md

Learning repo for spec-driven development + swarming agents / agentic autonomous loops with CrewAI.

## State
- App MVP is runnable: FastAPI backend (`app/main.py`, `POST /route`), Svelte + Vite + Leaflet frontend (`frontend/`), SQLite cache (`cache.db`, gitignored). OSRM demo supplies interim geometry (car profile; Mapbox walking in 008). Comfort scoring is still neutral — `001-T3` (Overpass provider) is done; T7–T10 remain.
- Specs are the source of truth: work goes `spec.md` → `plan.md` → `tasks.md` under `specs/NNN-name/`; decisions in `docs/architecture/`; durable docs in `docs/`.
- SDD layout (Option 2, Spec-Kit style): constitution in `.specify/memory/constitution.md`, transient work in `specs/NNN-name/` (`contracts/` when needed). Templates in `.specify/templates/`.
- Swarm (learning goal 2, `specs/009-swarm-harness/`): pure CrewAI coders + parallel Textual dashboard, prefix routing (`ollama/*` local → `zen/*` Zen → OpenRouter) with the operator `.env` cloud-only since 2026-11-14 (DeepSeek planner, `zen/glm-5.3-flash` coder, free Nvidia QA, `SWARM_LOCAL_FIRST=0`). Usage: `swarm/README.md`.
- Gate ownership (015): QA is the only agent that runs gates; every coder crew gets `ShellTool(allow_gates=False)` and works from QA's report (per-gate argv, exit code, failure output). The harness records each execution in `<run>/shell_log.jsonl` and derives green from those records (`qa_gate_missing` when stale/missing), so truthful green no longer needs the flow to re-run gates (`SWARM_TRUST_QA_EVIDENCE=0` restores that). Fix rounds are QA→coder→QA, max 3.
- Coder self-check (017, `specs/017-coder-selfcheck/`): between the micro-steps and QA the harness runs the project's *static* checks (type checker + linter, never the test suites — `SWARM_SELF_CHECK_COMMANDS` or the static subset of `SWARM_GATE_COMMANDS`) and hands a red one back to the coder as a bounded fix round (`MAX_SELF_CHECK_ROUNDS`). It is not a gate: its executions use their own agent role (`harness-selfcheck`), so they are never QA evidence and cannot make a run green. `SWARM_SELF_CHECK=0` disables; `run.json.self_check` records it.
- Scenario verifier (019, `specs/019-scenario-verifier/`): between the self-check and QA (and again after a QA fix round that changed the delta) a read-only crew answers *does the implemented scenario do what the brief says?* It sees the brief, the referenced ACs, the plan lines, the **full content** of every delta file (`FullFileReadTool`, `SWARM_VERIFY_READ_CHARS` default 60000 — the coder keeps the 3000-char trimmed read) and a static import/imported-by view. Its verdict is about the scenario, not the gates; on `BLOCKED` it emits correction steps in the planner's `STEP n:` format, which the flow runs through the step coder crews (`coder:verify<n>`) and re-verifies, bounded by `MAX_VERIFY_ROUNDS` (2). It has no write tools, runs no gate, has its own role (`verifier`), and cannot make a run green; a non-converging block ends as `needs_human` / `reason_code=verifier_blocked`. `SWARM_VERIFY=0` disables; `run.json.verifier` records verdict, rounds, findings, plan, files and model.
- Dark-factory hardening (`specs/012-dark-factory-harness/`, Phase 1 T11–T18 done): run-delta attribution (only this run's changes are gated/committed), tool-level scope + secret guards, argv-only shell, reviewer `PASS` required, vacancy guard on cached plans, content-hashed plan cache, commit/push coupled to green, single-run lock/PID/signals, approval holds, role-aware prompts, AC evidence + token/cost/timestamps in `run.json`, preflight, retry/backoff + model fallbacks, per-run budgets (`budget_exhausted`), listener teardown, incremental TUI tail, branch-per-task + `--no-ff` merge queue with rollback (`merge_failed`), a container sandbox (repo-only mount, `.env` masked), and an operator dashboard (ADR-011: queue outcomes, models/fallback, budget gauges, gates, recent runs). Gates run locally via `make` targets; there is no CI workflow.

## Harness lessons (learned from runs, keep in mind before "fixing" the swarm)
- **Read the run before theorising.** `run.json` first (`status`, `reason_code`, `gates`, `usage.models`, `usage.by_role`, `cost`, `budget`), then `events.jsonl` (`at` deltas = per-call latency), then `shell_log.jsonl` (gate argv/exit/output). A pretty TUI error is only a rendering of one of those.
- **`reason_code` can lag the real stop.** 007-T5 ended `reviewer_no_verdict` while the actual cause was the per-task cost cap: QA was never called. Cross-check `cost` vs `budget.max_cost_per_task` and the log for `qa crew failed`. Budget stops now re-raise as `_BudgetExhausted` (terminal, reported as `budget_exhausted`), and the QA review is **not** budget-gated — it is local/free and decides work that is already paid for.
- **Fallbacks are per role with one configurable local target.** A coder transport blip must never move QA: 007-T4 lost 30 minutes because one global `activate_fallbacks()` put the reviewer on `qwen3.5:9b`, which looped over the report and never declared a verdict. Now `SWARM_LOCAL_FALLBACK_MODEL` (default `ollama/swarm-coder:latest`) is the fallback for every role, `SWARM_<ROLE>_FALLBACK_MODEL` overrides per role, and only a provider-wide quota wall switches all roles at once. A missing QA verdict is decided by the senior model (`SWARM_SENIOR_MODEL`), never a paid one.
- **Never conclude "the provider is slow" from one error string.** Measure: events carry `at`, and a 120.5 s failure is 2×60 s (one SDK retry), not a slow model. A *fix* generation is not a 1–7 s chat call — 60 s cut a real fix off twice in a row (007-T5), so the cloud timeout is 180 s with SDK retries off (the harness retries once and logs it).
- **Statuses name the loop, not the task.** `needs_human`/`crew_error` usually mean the harness stopped itself; read `fix_rounds`, `dev_attempts`, `senior_used`, `evidence_note`, and the gate tails before blaming the code.
- **A green task that "reopened" is usually a key mismatch.** 007-T5 was green on 2026-11-09 and re-ran the next morning because its trailer said `Swarm-Task: 007/T5` (the invocation prefix) while the queue looked up `007-live-position/T5`. Before assuming the spec changed, compare `git log --grep 'Swarm-Task:'` against `swarm/spec_loader.py` `spec_dir_name()`, and check `_open_task_ids()` in `swarm/flow.py`. **Check the ledger entry points at the artifact**: 007-T9's green commit (`1f4b3d9`) contains only Mapbox files — the integration test it claims was never written — so a hash match alone is not proof; `git show --stat <sha>` should show the files the brief names.
- **Green means the gates passed, not that the task was done.** Six 014 tasks were committed green; T2's `GET /geocode` was never mounted in `app/main.py`, T7's client targets a path and a response key that the pinned contract does not use, T8 wired no selection, and T6/T9 never landed — all green, because a *missing* piece produces no failing assertion. Before trusting a green commit, compare the files it touched with the files the brief names, and check the endpoint is actually mounted (`grep '"/geocode' app/main.py`). A scenario verifier (spec 019) is the systematic answer.
- **Watch which task a run actually is.** `meta.json` is authoritative: the queue advances past done-ledger entries, so `run.sh 007 T4` can execute T5. Checkpoints are plan-hashed (`restarting … plan changed`).
- **A conflicted `git stash pop` is not a merge conflict.** 2026-11-10: T8 (014) popped its stash onto the base it had just merged and conflicted on `App.svelte`; the harness printed `STASH RESTORE FAILED`, kept the stash, and left three `UU` stages in the tree — the next three runs gated around conflict markers. Preflight now blocks on `git diff --diff-filter=U`, and the stash is always archived as `refs/swarm/archive/<stamp>-<sha>` with `stash_conflict`/`stash_conflict_ref` in `run.json`. A conflicted restore is **resolved**, not parked: a `Stash Conflict Resolver` crew (read + edit only) re-applies the parked side on the newer tree, accepted only when no marker remains, only conflicted files were edited, and every gate is green; otherwise it falls back to `--ours` and records `stash_conflict_resolution` (`crew`/`ours`/`kept`) + `stash_conflict_note`. Orphaned `swarm-*` stashes are swept at kickoff (archived as refs, indexed in `swarm/runs/orphan_stashes.json`, then dropped; `SWARM_ARCHIVE_STASHES=0` disables). No human step, and no user stash is ever touched — inspect with `git show <ref>:<path>`, never `git stash pop`.
- **A stuck task is usually a missing report, not a hard problem.** 007-T9 (2026-11-10) burned five fix rounds on a broken test file: the report was rendered in gate order and cut at 9000 chars, so the vitest failure never reached the coder. The report now puts failing gates first with extracted `file:line: message` key lines (14k budget), and a fix round that changes nothing ends the round (`no_progress`). Read the report the coder actually receives (`run.json.qa_report` → `report_text`) before blaming the model.
- **Deterministic style failures are not coder work.** The harness repairs them itself: when the only red gate is a lint/format gate and its output names nothing but formatting, the flow runs `SWARM_STYLE_FIX_COMMAND` (`npm --prefix frontend run lint:fix`) and re-checks it (`run.json.style_autofix`). A red type check or red test is never treated as style — that is coder work.
- **A type error is not a QA round-trip.** 007-T9 (2026-11-11) spent three QA rounds and two coder rounds on `Property 'tick' does not exist on type 'PositionProvider'`: the checker named the file, the line and the cause, and the fix rounds still did not land it (one round changed no file at all → `no_progress`). The harness now runs the static checks itself right after the micro-steps and gives the coder the same `file:line: message` report QA would have given him, before QA is invoked (`run.json.self_check`). When a run is "stuck on a linter bug", look for the self-check record first: if it is absent, the run predates 017 or the phase is off.
- **The coder may not own the module the test exercises.** The same 007-T9 run wrote its own `frontend/src/lib/navigation/walkMode.ts` because the real store (`frontend/src/lib/walkMode.ts`, green in T6–T8) was not in the plan — a duplicate implementation that would have been committed as part of a *test* task. Before writing a module, check the spec's plan and `git log --grep 'Swarm-Task:'` for an existing owner of that path; the queue order (T6→T9) is not a guarantee that the earlier task landed.
- **A truncated read is a loop, not a hint.** 014-T1 (2026-11-12) spent 50 minutes and 229 calls on one wrong string. The read tool caps observations at 3000 chars and said "re-read with start_line/line_count" — so the coder asked for lines 1–500 of a 178-line file **seven times** and got the same first 85 lines every time, never seeing `search()` at line 169; it re-read, changed nothing, and the run ended `no_progress`. The truncation note now names the exact line to continue from (`CONTINUE with start_line=<n>`). When a run ends `no_progress`, check the read log for a repeated read of the same range before blaming the coder.
- **A `needs_human` run needs a reason you can copy.** The dashboard's `h` screen is not pasteable. Every run now writes `<run_dir>/human_log.txt` (stop reason, reason code, failing gates, verdict, changed files); `make swarm-log` prints it. Read that file first — it is the whole story in one screen.
- **Do not show a budget cap that cannot fire.** The panel read "tokens 1.7M / 2.0M 84.0%" for a run whose token/dollar caps are *not enforced* (`free_local_run: true`), which reads as "the budget stopped this". A free-local run now shows "no cap: free local run".
- **A red run needs a verdict most of all.** The reviewer got 9 iterations for 6 gates + `git status` + the verdict, so it re-ran `pytest` and never concluded: `review_verdict: "unknown"` left the fix rounds with no grounded reason. The budget is 12 and the verdict repair now runs on red runs too (it used to run only when the gates were green).
- **Measure with the replay set, not with memory.** `make swarm-bench` (020) renders the real prompts and reports from 12 frozen green runs with no model call. It is the only way to tell whether a change removed work or moved it; run it before and after, and use `SWARM_CONTEXT_COMPACT=0` / `SWARM_GATE_SELECT=0` / `SWARM_PROMPT_CACHE=0` to restore the old behaviour for an honest A/B. A token win that lowers the green rate is not a win; `make swarm-bench-live CASE=<id>` is the check that the loop still reaches green.
- **Three shapes for one field means no shape is right.** 014-T1 was not a typo: `plan.md`, the green `contracts/geocode.json` and the coder's module each defined `Suggestion` differently (and the token variable a third way). Before blaming a coder for a contract mismatch, diff the three sources — `plan.md`, the committed contract, and the code — and pin one.

## Commands (verified 2026-11-08)

## Boundaries / entrypoints
- `app/` + `tests/` → root `.venv` (app deps only). `swarm/` → `swarm/.venv` (CrewAI). `frontend/` → npm. Do not mix them.
- Backend entrypoint: `app/main.py` (`app = FastAPI(...)`). `app/router.py` was removed; do not reintroduce a second app/route mount.
- API contract: `contracts/route.json` is the source of truth (ADR-005): `POST /route`, preference enum `hot`/`cloudy`, GeoJSON `geometry`, `{ code, message }` errors.
- Dark-factory Phase 2 (`specs/013-dark-factory-phase-2/`, done): done ledger from commit trailers (`Swarm-Task`/`Task-Hash`/`Spec-Hash`, so green-but-unchecked tasks are skipped and spec/plan edits reopen them), approval-resume commit of a held run's verified delta via the merge queue, and atomic per-step `progress.json` crash checkpoints (plan/file/age validated; gates+reviewer always rerun).
- Harness efficiency (020, `specs/020-harness-efficiency/`): `make swarm-bench` scores a frozen 12-case corpus with **no model call** — per case it builds the real crews and report and counts prompt chars, report chars and gates/round (baseline `swarm/bench/baseline.json`). Prompts come from `swarm/prompts.py` with a byte-stable per-task prefix (`prompt_prefix` hash recorded per case); full step outputs go to `<run>/step_outputs/` and long gate tails to `<run>/gate_logs/` (`SWARM_CONTEXT_COMPACT`), the inner loop runs only the affected gates with the full suite before green (`SWARM_GATE_SELECT`, `SWARM_GATE_MAP`), reports carry key lines once, coder crews get `Repo Search`, and `make swarm-bench-live CASE=<id>` replays one case in a throwaway worktree. Measured vs baseline: task prompt −6.6%, report −86%, inner-loop gates −40%. The −30% prompt-char target is recorded as missed (per-step agent/tool overhead dominates), not claimed. Control-plane spec, skipped by the queue.
- Fix loop (021, `specs/021-fix-loop/`, implemented): the measured waste after 020 is the second round (59% of green runs, 44.6% of prompt tokens, 3× wall clock). It now has an outcome replay suite (`make swarm-replay`, `--off` A/B), per-round `fix_cause` telemetry, deterministic repair before QA, a tests-first A/B (`SWARM_TESTS_FIRST`), an AC-aware coder prompt A/B (`SWARM_CODER_ACS`), `SWARM_CODER_LOOSE`/`SWARM_PLAN_MAX_STEPS` A/Bs, repair-budget/checkpoint policy (`SWARM_MAX_FIX_ROUNDS`, `best_delta`), verification ROI (`self_check.hit`, `verifier.hit`), verifier stability (`overridden`/`stalled`/`unstable`) and a step-landing check. **Measurement is incomplete**: the baseline run produced `005` `verifier_blocked` (747 s), timed out on `004`/`006` at 2400 s, and never reached `007`/`010`, so `swarm/bench/replay_baseline.json` is `complete: false` and the AC-9 targets are recorded as not evaluated. The harness correctness fixes are validated (the verifier now passes after a correction and QA is reached); the loop still does not converge on these cases, so the next step is a model bake-off and a faster case set. Investigation: `docs/research/fix-loop-2026.md`. Control-plane spec, skipped by the queue.
- Lean loop (022, `specs/022-lean-loop/`, implemented, measurement partial): phase timing from events (monotonic stamps; roles resolved by crew object because CrewAI emits from its own thread), a per-task wall budget (`SWARM_TASK_WALL_BUDGET`, stop reason `wall_budget`, checked between phases and before retries, with each agent capped at the remaining budget), separate fix/verifier timeouts (`SWARM_LLM_FIX_TIMEOUT_SECONDS`) with `llm_timeout` records and `run.json.retries`, opt-in concurrent verifier∥QA (`SWARM_VERIFY_CONCURRENT`), an opt-in docs-only lean verifier path (`SWARM_VERIFY_LEAN`, the class-0/1 seed), and a `last_phase` record when the runner kills a case. Measured: the budget stops a case with a `run.json` instead of an anonymous timeout; **the first live green exists** — `004-weather-sun-T2` at 433 s, 176k tokens (78k cached), $0.0414, one fix round (`replay_baseline.json`, `complete: false`); `004-T3` was also green (315.6 s, $0.029) in the same worktree. The five-case suite and the AC-6 wall-clock target are still not measured; concurrency and the lean path stay off until an A/B wins. Budget defaults are 1800 s wall, $1.00/cost and 2400 s per task. Control-plane spec, skipped by the queue.
- Parallel factory (023, phase 1, implemented): `make swarm-parallel BATCH="spec:task,..."` runs independent tasks in detached worktrees with the current harness (`--no-commit`), takes up to `SWARM_WORKERS` from a group whose briefs name disjoint files, and integrates only greens **serially**: `git apply --check` → apply → full gates on the main tree → commit with the standard trailers → best-effort push. A conflict or failed gate reverses the patch and leaves the task open; the main tree has one writer. Live throughput is **not measured** yet (no green baseline). Control-plane spec, skipped by the queue.
- Earned autonomy (024, implemented, off by default): `swarm/risk.py` classifies a run 0 docs / 1 tests / 2 logic (`app/`, `frontend/src/`, `contracts/`) / 3 control (`swarm/`, `specs/`, migrations, auth/payments/infra, config, unknown); a sensitive brief forces 3. `SWARM_AUTONOMY=1` + `SWARM_AUTONOMY_MAX_CLASS=1` lets class 0/1 skip the `awaiting_approval` hold **only** when every gate is green, the reviewer passed and the verifier is not blocked; the commit still goes through the branch/merge-queue/trailer path. `run.json.autonomy` records the class, inputs, decision and reason; `human_log.txt` and `make swarm-report` show it. No live auto-merge is claimed yet (no green baseline); escape-rate measurement is the next decision. Control-plane spec, skipped by the queue.
- Durable journal (025, ADR-012 option C first slice, implemented): `swarm/journal.py` is a SQLite/WAL append-only journal with idempotent `(run, key)` events, step status/attempt/**leases** (atomic claim, owner-only heartbeat, TTL), an **effects** table (`commit:<run>:<delta>` makes a retried commit a no-op) and `fold(run)` as the projection in `run.json.journal`. The flow writes `run_started`, seeds/completes steps, resumes from the journal's contiguous completed prefix when it is longer than `progress.json` (recovery note `journal`), and records the commit effect. `run.json`, `events.jsonl` and `progress.json` remain the operator views; green is still QA's evidence. No dispatcher/workers/Postgres yet — those are the ADR triggers. Control-plane spec, skipped by the queue.
- Escape rate (024): `make swarm-report` joins `run.json.autonomy` with git (`This reverts commit <sha>`) and reports escapes per class. It is a floor (a hand-fixed regression is not counted); widening to class 2 waits for it.
- Earned autonomy was switched on in the operator `.env` on 2026-11-14 (`SWARM_AUTONOMY=1`, max class 1): class 0/1 greens may auto-merge after gates + verifier; the code default stays 0 so a fresh checkout is safe. Watch the class and reason in `human_log.txt`/`run.json.autonomy` and build the escape-rate ratio before widening to class 2.
- Swarm queue: the harness reads only unchecked `- [ ] T<n> (AC-…): brief` lines from `specs/*/tasks.md`, in directory order; authoring rules + scope/`--replan` notes are in `swarm/README.md` ("Adding a spec to the swarm todo list"). Harness specs (`009`, `012`–`025`) are always skipped (control plane; the list is `HARNESS_SPECS` in `swarm/flow.py`). The swarm does not edit spec files — mark `[x]` yourself after green (or rely on the 013 done ledger). Non-green statuses: `needs_human`, `awaiting_approval`, `commit_failed`, `push_failed`, `merge_failed`, `crew_error`, `quota_exhausted`, `budget_exhausted`, `interrupted`, `preflight_failed`.
- Do not invent commands or config. Verify via manifests/scripts before claiming a workflow exists.

## Spec-driven workflow
- Spec before code: define requirements, acceptance criteria, and scope in `specs/` before implementing.
- Clarify first: when requirements are ambiguous, ask the user targeted questions (via `question` tool, 1–2 at a time) and refine the spec docs until clear. Do not guess or implement on ambiguity.
- Update tasks/ACs in the same change as the implementation. Record completed work and remaining blockers explicitly (see `specs/001-example-app/tasks.md` T3/T7–T10 and `specs/011-dev-run/`).
- Keep specs small and verifiable; link implementation back to spec items.
- Prefer editing existing files over creating new ones; keep changes minimal per spec.
